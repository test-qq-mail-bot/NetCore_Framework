# NetCore Framework 构建与交付指南

> **适用框架版本**：NetCore Framework 20260721-v49（程序内置版本号，随发布递增）
> **最后更新**：2026-07-21
> **配套脚本**：`build.bat`（Windows 一键编译）、`build.sh`（Linux/macOS 一键编译）、`build.py`（跨平台单文件构建内核）、`Dockerfile.linux`（Linux 可复现构建）

本文件说明两件事：

1. **如何使用源代码**——以开发者身份把项目跑起来、改代码、调接口。
2. **如何编译单文件可执行文件**——产出 Windows `netcore-framework.exe` 与 Linux `netcore-framework`，用于无 Python 环境交付。

---

## 一、源代码结构（速览）

```
NetCore Framework/
├── main.py                      # 程序入口：uvicorn 启动 FastAPI 服务
├── core/                        # 框架核心（路由、鉴权、插件加载、配置、日志）
│   ├── framework.py             # FastAPI app、插件前端 manifest 接口、版本号
│   └── config_loader.py         # 系统版本 SYSTEM_VERSION（内置版本号唯一来源）
├── plugins/
│   └── netconfig_guardian/      # 数通配置卫士插件
│       ├── plugin.py            # 后端路由（设备/备份/差异/任务日志等）
│       ├── db.py                # SQLite 数据访问
│       └── frontend/            # 前端页面（每页一个 JS，经 window.NC.registerPage 自注册）
│           ├── devices.js        # 设备管理（含设备详情抽屉）
│           ├── tasks.js          # 任务管理
│           └── task-monitor.js   # 右下角任务监控浮窗
├── frontend/                    # 框架前端（index.html + app.js + ui/framework.js）
├── wiki/                        # 文档（随 EXE 打包，编译时快照）
├── requirements.txt             # 运行时依赖（全跨平台，无 Windows 专属包）
├── build.bat                    # 【最简】Windows 一键编译（双击即可，自动建 venv/装依赖/编译）
├── build.sh                     # 【最简】Linux/macOS 一键编译（chmod +x 后 ./build.sh）
├── build.spec                   # 旧版 Windows 专属 PyInstaller 配置（写死 ROOT）
├── build.py                     # 跨平台构建内核（动态生成 spec，被上面两个脚本调用）
├── Dockerfile.linux             # Linux 构建镜像
└── dist/                        # 构建产物输出目录（netcore-framework[.exe]）
```

**版本号规则**：唯一来源是 `core/config_loader.py` 的 `SYSTEM_VERSION`（如 `20260721-v49`），
`core/framework.py` 的 `FastAPI(version=...)` 应与之一致。前端登录后通过 `GET /api/system/info`
的 `version` 字段读取（注意：`/api/auth/login` 响应**不含** version 字段）。

## 二、如何使用源代码（开发模式）

### 2.1 环境要求
- Python **3.10+**（已在 3.13 验证）。
- 建议用虚拟环境隔离依赖。

### 2.2 安装依赖
```bash
# 1) 创建并激活虚拟环境
python -m venv venv
# Windows 激活：
venv\Scripts\activate
# Linux / macOS 激活：
source venv/bin/activate

# 2) 安装运行时依赖（已含全部插件依赖，含数通配置卫士的 netmiko、运维常用工具箱的 paramiko/pyftpdlib/dnspython/tftpy 等）
pip install -r requirements.txt
```

### 2.3 启动（开发运行）
```bash
python main.py
```
- 默认监听 `0.0.0.0:8080`（浏览器访问 `http://127.0.0.1:8080`）。
- 日志输出到控制台，格式 `[时间] [级别] 消息`。
- 首次运行会在工作目录生成插件数据（如 `plugins/netconfig_guardian/data/guardian.db`）。

### 2.4 默认账号
- 用户名：`admin`
- 密码：`Admin@123!`
- 登录接口：`POST /api/auth/login`（返回 `token`，后续请求带 `Authorization: Bearer <token>`）。

### 2.5 前端静态资源约定（改界面时注意）
- 每个插件页是一个独立 JS，在 `plugins/<plugin>/frontend/*.js` 中，
  通过 `window.NC.registerPage(...)` 自注册，由框架前端按路由动态加载（含 `task-monitor.js`）。
- **源目录 `plugins/.../frontend/` 即打包输入**；修改后需重新编译才能进入 EXE。
- 路由为 History API（非 hash），`#/guardian/devices` 这类链接是前端内部分发，
  实际路径是 `/guardian/devices`。

### 2.6 运行接口测试
参考 `tests/smoke_v49.py`：登录 → `GET /api/system/info` 校验版本 → 全模块接口冒烟。
也可直接 `curl`：
```bash
curl -s -X POST http://127.0.0.1:8080/api/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"username":"admin","password":"Admin@123!"}'
```

## 三、如何编译单文件可执行文件

> PyInstaller **不支持交叉编译**：在 Windows 上只能产出 `.exe`，在 Linux 上只能产出 Linux 可执行文件。
> 因此「一次生成两种」需要分别在不同操作系统（或用 Docker）构建。

### 3.1 最简：一键脚本 `build.bat` / `build.sh`（推荐，无需手敲命令）
不熟悉命令行也能用——脚本会**自动检测 Python → 创建 `.venv` 虚拟环境 → 安装全部依赖（含 PyInstaller、netmiko）→ 调用 `build.py` 编译 → 打印产物路径**。

- **Windows**：直接**双击 `build.bat`**（或命令行执行 `build.bat`）。
  ```bat
  build.bat                 :: 默认编译到 dist\netcore-framework.exe，结束会暂停等你查看结果
  build.bat --dist outdir   :: 可选：把产物输出到 outdir（参数透传给 build.py）
  ```
- **Linux / macOS**：
  ```bash
  chmod +x build.sh     # 首次赋予执行权限
  ./build.sh            # 编译到 dist/netcore-framework
  ./build.sh --dist outdir   # 可选：指定输出目录
  ```

> 前置条件：机器已安装 **Python 3.10+** 并加入 PATH（Windows 安装时勾选 "Add Python to PATH"；Linux 需 `python3` 与 `python3-venv`）。脚本首次运行会联网安装依赖，耗时取决于网络；之后复用 `.venv`，再次编译更快。
> 跨平台限制同下：`build.bat` 只产出 Windows EXE，`build.sh` 只产出 Linux/macOS 可执行文件（PyInstaller 不支持交叉编译，需 Linux 产物见 3.4 Docker 方式）。

### 3.2 进阶：`build.py`（跨平台内核）
`build.py` 会**以自身所在目录为项目根 ROOT**（不再写死绝对路径），运行时动态生成
与 `build.spec` 对齐的 PyInstaller 配置，并把产物放到 `dist/`。若已自备 Python 环境与依赖，可直接调用它（一键脚本内部也是调用它）。

```bash
# 构建当前系统对应的可执行文件（Windows→.exe / Linux→无后缀）
python build.py

# 指定平台
python build.py --target win      # 当前须为 Windows 环境
python build.py --target linux    # 当前须为 Linux 环境

# 一次构建两者（跨系统的那一个走 Docker，见 3.4）
python build.py --target all

# 指定输出目录（默认 dist/）
python build.py --dist outdir
```
构建成功后脚本会打印产物**路径、体积、MD5**，便于交付核对。

### 3.3 Windows 原生构建
在 **Windows** 机器上（依赖已装、PyInstaller 已装）：
```bash
python build.py --target win
# 产物：dist/netcore-framework.exe
```
也可用旧版写死路径的 spec（仅限当前 Windows 绝对路径不变时）：
```bash
pyinstaller build.spec --noconfirm
```

### 3.4 Linux 原生 / Docker 构建
- **在 Linux 机器上**（最省事）：
  ```bash
  python build.py --target linux
  # 产物：dist/netcore-framework
  ```
- **在 Windows / macOS 上，借助 Docker 一键产出 Linux 文件**（需本机安装 Docker）：
  ```bash
  # 1) 构建镜像
  docker build -f Dockerfile.linux -t nc-framework-build .

  # 2) 运行并把产物写回宿主机 dist/（挂载卷）
  #    Windows：
  docker run --rm -v "%cd%/dist":/out nc-framework-build
  #    Linux / macOS：
  docker run --rm -v "$PWD/dist":/out nc-framework-build
  # 产物：dist/netcore-framework（已 chmod +x）
  ```
  `Dockerfile.linux` 基于 `python:3.13-slim`，安装编译依赖 + `requirements.txt` +
  `PyInstaller` + `netmiko` 后调用 `build.py --target linux --dist /out`。

### 3.5 产物命名与校验
| 平台   | 产物文件名                | 说明 |
|--------|---------------------------|------|
| Windows | `dist/netcore-framework.exe` | 单文件，双击即运行（控制台窗口） |
| Linux   | `dist/netcore-framework`      | 单文件，`./netcore-framework` 运行（需可执行权限） |

- 单文件 EXE 首次运行会解压到系统临时目录再启动，属正常行为。
- 交付前建议记录 MD5（脚本已打印），客户端可用 `certutil -hashfile`(Win) /
  `md5sum`(Linux) 核对完整性。
- **交付内容就是这一个文件**：`frontend/`、`plugins/`、`wiki/` 等资源已全部打进单文件，
  无需随产物附带任何目录。程序**首次启动时会在 EXE 所在目录自动生成**
  `config/`（配置与账号哈希）、`data/`（数据库与运行数据）、以及 `frontend/`、`plugins/`、
  `wiki/` 的运行时副本——这些都是运行产物，打包交付时不要一起打包。

### 3.6 交付后的运行
```bash
# Windows
dist/netcore-framework.exe
# Linux
chmod +x dist/netcore-framework && ./dist/netcore-framework
```
访问 `http://127.0.0.1:8080`，用 `admin / Admin@123!` 登录。

> 请把 EXE 放在**有写入权限**的目录（不要放在 `C:\Program Files` 等受保护路径），
> 否则首次启动生成 `config/`、`data/` 会失败。

### 3.7 交付自检脚本 `verify_dist.py`
项目根提供 `verify_dist.py`，用于在**交付位置原地**拉起 `dist/` 下的产物做一次真实客户
场景验证：启动 → 登录（`admin/Admin@123!`）→ 校验插件版本（自动读取
`plugins/ops_toolbox/routes/common.py` 的 `PLUGIN_VERSION`，不写死）→ 抽查一个工具接口
→ 统计运行日志报错行数，最后打印 `ALL PASS` 或 `FAIL`。

```bash
python verify_dist.py     # 需要 httpx；返回码 0 表示全部通过
```

## 四、常见问题（FAQ）

- **Q：`No module named 'sqlite3'` / 某些模块打包后缺失？**
  A：这些模块在运行时被 `importlib` 动态加载，静态分析抓不到。`build.py` 已在隐藏导入中
     显式加入 `sqlite3`、`openpyxl` 等；若仍缺失，确认对应包已 `pip install` 进构建环境。
- **Q：打包体积暴涨（GB 级）？**
  A：`build.spec`/`build.py` 已 `exclude` 掉 `pandas/scipy/torch/numpy/matplotlib`
     （openpyxl 仅写 xlsx，不需要这些）。若自行改动隐藏导入请留意。
- **Q：在 Windows 上能直接产出 Linux 文件吗？**
  A：不能（PyInstaller 不交叉编译）。请用 3.4 的 Docker 方式，或到 Linux 机器构建。
- **Q：`build.bat` / `build.sh` 和 `build.py` 是什么关系？**
  A：`build.bat`（Windows）和 `build.sh`（Linux/macOS）是**傻瓜式一键封装**——自动检测 Python、
     创建 `.venv`、安装依赖、再调用 `build.py` 编译，适合不想手敲命令的人；已经配好环境的开发者
     可直接用 `build.py`。两者产物完全一致。脚本额外参数（如 `--dist`）会透传给 `build.py`。
- **Q：一键脚本报"未检测到 Python"？**
  A：说明系统 PATH 里没有 Python。请安装 Python 3.10+（Windows 勾选 "Add Python to PATH"；
     Linux 装 `python3` 与 `python3-venv`）后重新运行脚本。
- **Q：`build.py` 与 `build.spec` 用哪个？**
  A：**优先 `build.py`**——路径动态、跨平台、产物自动命名与 MD5 打印。`build.spec` 仅作为
     历史 Windows 专属配置保留，依赖写死的绝对路径，迁移项目后不可用。
- **Q：前端改了但 EXE 里没生效？**
  A：EXE 用 `plugins/.../frontend/` 源目录打包。改完前端后**重新编译**；若同时维护
     `dist/plugins/...` 镜像，记得源与镜像同步（历史交付流程如此），再构建。
- **Q：端口被占用？**
  A：默认 8080；若被占，修改 `main.py` 中的端口后重新编译，或运行时改配置。
