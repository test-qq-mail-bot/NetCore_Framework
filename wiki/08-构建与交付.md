# 08-构建与交付

本文档覆盖构建环境、build.py 用法、CI 流程、版本号规则、测试环境、交付规范。

---

## 1. 构建环境准备

### 1.1 Python 环境

```bash
# 推荐 uv（速度快、依赖解析可靠）
uv venv --python 3.13 .venv

# 安装运行时依赖 + 构建期依赖
uv pip install -r requirements.txt -r requirements-dev.txt --python .venv
```

### 1.2 依赖分层

| 文件 | 用途 | 特点 |
| --- | --- | --- |
| requirements.txt | 运行时依赖 | 全部 `==` 精确锁定，含全部官方插件依赖与 tzdata |
| requirements-dev.txt | 构建期依赖 | pyinstaller + pytest + ruff |

**重要**：新增运行时依赖必须精确锁定版本并在行内注释用途。

### 1.3 UPX（可选压缩）

存在 `tools/upx.exe` 或在 PATH 中时，PyInstaller 自动启用 UPX 压缩，减小产物体积。

## 2. 本地构建

### 2.1 构建命令

```bash
# Windows
python build.py --target win

# Linux（需 Linux/Docker 环境）
python build.py --target linux

# 双平台（跨系统项走 Dockerfile.linux）
python build.py --target all

# 自定义产物目录
python build.py --target win --dist /path/to/output
```

### 2.2 构建流程

1. 读取 `core/config_loader.py` 的 `SYSTEM_VERSION` 作为版本号
2. PyInstaller onefile 模式打包
3. `frontend/`、`wiki/`、`plugins/` 整目录打入资源包（新增文件无需改清单）
4. 构建产物自动打印：体积、MD5、SHA256、时间戳
5. 构建工作目录 `_pyi_work` 构建后自动删除

### 2.3 产物

```
dist/
├── netcore-framework.exe          # Windows 产物
└── netcore-framework              # Linux 产物
```

## 3. 测试

### 3.1 运行测试

```bash
# uv 环境（推荐）
.venv\Scripts\python.exe -m pytest tests -q

# 激活环境后
pytest tests -q

# 详细输出
pytest tests -v
```

当前测试：7 个用例，覆盖核心功能。

### 3.2 Lint

```bash
.venv\Scripts\python.exe -m ruff check core plugins main.py build.py
```

ruff 检查代码风格与常见错误。CI 中 `|| true` 非阻断（仅警告）。

### 3.3 前端检查

前端为离线全局构建（Vue3 + ElementPlus），无独立构建步骤。修改前端 JS 后直接刷新浏览器即可（SPA 运行时编译）。

## 4. CI 自动构建（GitHub Actions）

配置文件：`.github/workflows/build.yml`

### 4.1 触发条件

| 事件 | 行为 |
| --- | --- |
| push 到 main | 自动构建（test → windows → linux） |
| 打 `v*` 标签 | 自动构建 + 发布 Release |
| 手动 workflow_dispatch | 可选发布 Release |

### 4.2 流水线

```
test job:
  checkout@v5 → setup-python@v6 → 安装双 requirements → ruff（|| true）→ pytest（阻断）

windows job:
  checkout@v5 → setup-python@v6 → pip install → python build.py --target win → upload-artifact@v5

linux job:
  checkout@v5 → setup-python@v6 → pip install → python build.py --target linux → upload-artifact@v5

release job（仅手动触发且勾选 publish_release）:
  download-artifact@v5 → 汇集 win/linux 产物 → 按 SYSTEM_VERSION 打 tag → GitHub Release 发布
```

### 4.3 Artifact 版本

CI 使用 `actions/upload-artifact@v5` + `actions/download-artifact@v5`。

## 5. 版本号规则

### 5.1 格式

`变动日期-V序号`，如 2026 年 8 月 26 日第 6 个版本 = `20260826-V6`。

### 5.2 谁改动谁升版

| 场景 | 升级位置 |
| --- | --- |
| 改 NetCore-Framework 核心 | `core/config_loader.py → SYSTEM_VERSION`（单点维护） |
| 改某插件 | 该插件的 `plugin.py → get_metadata()` 中的 version |
| 仅改文档 | 不升版 |
| 仅改前端静态资源 | 不升版（缓存由 `?v=` mtime 控制） |

### 5.3 版本号存储

- 后端：`core/config_loader.py` 第 87 行 `SYSTEM_VERSION = "20260826-V6"`
- 前端：`frontend/ui/framework.js` 第 184 行 `NC.FRAMEWORK_VERSION = "20260824-V2"`（前端版本独立维护）
- 插件：各自 `plugin.py` 的 `get_metadata()` 返回值

## 6. dist 目录规则

### 6.1 清空规则

每次构建前**清空 dist 目录**，只保留最新可执行文件。

### 6.2 部署目录与构建目录分离

- 构建目录：`源代码/NetCore-Framework/dist/`
- 部署目录：`C:\Users\Administrator\Desktop\ai-agent\NetCore-Framework\dist\`

替换部署目录 exe 前：
1. 确认进程已退出（Windows 文件锁导致覆盖失败）
2. 备份运行数据（config/data/plugins）
3. 覆盖 exe
4. 启动

### 6.3 运行时数据备份

每次构建/部署前，将运行数据备份到 `.workbuddy/backup_YYYYMMDD_HHMM_dist_runtime/`。

## 7. 测试代码交付流程

1. 在临时工作区完成开发与自测（不污染源码目录）
2. 全部功能模块测试通过后，把测试代码复制回 `tests/`
3. 更新文档（本套 wiki + 根 README + API 手册）与对应组件版本号
4. 构建最新 EXE 到 dist 并校验哈希
5. 本地 commit 提交说明写明修复的 bug；**推送由维护者手动执行**

## 9. 新增依赖规范

1. 在 `requirements.txt` 中添加精确锁定版本
2. 行内注释用途：`requests==2.32.3  # HTTP 客户端（ops_toolbox API 调用）`
3. 同步更新 `requirements-dev.txt`（如需要）
4. 更新根 README.md 技术栈说明
5. 更新本文件（08-构建与交付）依赖表
6. 升版本号（SYSTEM_VERSION 或插件版本）
